# Test evidence, overnight build, Oct 26, 2026

Build: the W3 provenance seal library in this directory, from
`../SPEC.md`, per the coordinator's overnight directive. Everything
below was run locally on the Muse VM (Node v24.22.1). Nothing
touched World Chain, no real content was sealed, and no production
key exists in this work: tests use the published Hardhat/Anvil
default test keys, labelled as fixtures in `tests/helpers.js`.

## Commands and results

Canonicalisation vectors, generated by the independent Python
implementation in `vectors/generate_vectors.py`:

```
$ cd vectors && python3 generate_vectors.py
wrote 14 vectors to canonicalization.json
```

Full suite:

```
$ cd lib && npm install   (adds @noble/curves 1.9.7, @noble/hashes 1.8.0)
$ npm test                (node --test tests/*.test.js)
tests 39, pass 39, fail 0
```

The 39 tests, grouped:

- Canonicalisation (17): each of the 14 vectors byte-compared
  against the Python-generated canonical bytes and SHA-256
  (CRLF/CR mixes, trailing whitespace, trailing blank lines,
  missing final newline, empty and blank-only input, NFC combining
  characters, BOM, zero-width character preservation, interior
  blank lines, leading whitespace, emoji, mixed endings), plus
  idempotence on every vector and one-character-changes-the-hash.
- Seal round-trips (6): key-to-address against the known Hardhat
  account #0 address (an external known value, which cross-checks
  the keccak and secp256k1 derivation path), seal and verify
  round-trip, determinism, approved tier hard-disabled at seal
  time (throws `ApprovedTierDisabled`), and proof that the anchor
  and supersession annotations do not invalidate the signature.
- Failure states (10): the eight named states, each triggered by
  its own fixture (see `tests/failures.test.js`), the exact
  eight-name list asserted as a set, and the HUMANID RULE scan
  asserting the raw humanId string appears nowhere in a serialised
  verify result while its SHA-256 hash does.
- Anchoring (6): calldata shape, mock chain write and read-back
  with confirmations, the stacked World Chain provider refusing to
  write while unconfigured, the same provider working through
  injected writer/reader functions, an unconfigured provider
  surfacing in verification as `check-incomplete` (never a pass,
  never `anchor-invalid`), and anchored-hash mismatch producing
  `anchor-invalid`.

CLI harness, run end to end with the test key:

```
$ w3-seal hash demo.md       -> sha256:a959282d... (33 canonical bytes)
$ w3-seal seal demo.md ...   -> seal JSON written
$ w3-seal verify seal.json --content demo.md
  -> schema w3-verify-result/1, state "verified", failures [],
     signature pass (recovered 0xf39F...2266), content pass,
     agentbook pass with human_id_hash only, anchor skipped
     (signer-claimed), summary includes "Human approved: no"
$ w3-seal anchor-demo        -> seal + mock anchor + verify,
     state "verified", summary reports the World Chain anchor
     wording with the mock block time
```

Independent cross-implementation check, added after the suite
(coincurve/libsecp256k1 plus pycryptodome Keccak, neither sharing
code with the library's noble stack):

```
$ w3-seal seal demo.md ... (JS library, noble curves/hashes)
$ python3 cross-check: EIP-191 prefix + message, Keccak-256 via
  pycryptodome, public key recovery via coincurve
recovered:   0xf39fd6e51aad88f6f4ce6ab8827279cfffb92266
seal wallet: 0xf39fd6e51aad88f6f4ce6ab8827279cfffb92266
MATCH (and the test key independently derives to the same address)
```

So all three pillars are now checked against second
implementations: canonicalisation (Python unicodedata/hashlib
vectors), SHA-256 (Node crypto plus the vector hashes), and
EIP-191 sign/recover (noble versus libsecp256k1).

## Adapter addendum, Oct 26, 2026 (W0 verify core wired)

The W0 adapter (`src/agentbook-w0.js`) landed after the overnight
suite, on Nic's go. Suite is now 44 tests, 44 pass, on both Node 24
(VM) and Node 22 (Furnace): the five new tests pin the status
mapping (verified to hash, unregistered to null, unknown to throw),
constructor validation, identical `human_id_hash` from raw-form and
W0-form providers, and the canonical hash construction checked
against an independent node:crypto computation.

Live run on Furnace against the real @fiador/verify package and
the real AgentBook contract (`node scripts/live-w0-check.mjs`):

- Known-registered wallet (the Furnace playground wallet) resolves
  through the adapter to `human_id_hash`
  sha256:7bf4573c...7341b1 (a hash; the raw value never reaches
  this library through W0's public shape).
- Known-unregistered wallet (Hardhat test account #0) resolves to
  null.
- Dead RPC: the adapter throws "W0 verifyAddress returned unknown
  (lookup_failed)", which verifySeal reports as check-incomplete.
- verifySeal end to end, live: the fixture seal passes signature
  and fails AgentBook as wallet-not-registered; a seal record
  naming the registered wallet passes the AgentBook check with the
  identical hash while its signature check fails, as it must (the
  fixture key does not hold that wallet, and the checks report
  separately by design).
